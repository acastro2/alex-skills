# Traces (to Tempo)

Traces are the backbone. Logs, metrics, and profiles all hang off the active span's context, so get tracing right first.

## Auto-instrumentation (free spans)

Install and register the instrumentation that matches the app's libraries (`setup.md`). Each produces spans with OTel semantic-convention attributes:

| Package | Spans for |
|---|---|
| `OpenTelemetry.Instrumentation.AspNetCore` | inbound HTTP requests (server spans) |
| `OpenTelemetry.Instrumentation.Http` | outbound `HttpClient` calls (client spans) |
| `OpenTelemetry.Instrumentation.SqlClient` | SQL Server commands |
| `OpenTelemetry.Instrumentation.EntityFrameworkCore` | EF Core queries |
| `Npgsql.OpenTelemetry` | Npgsql/Postgres |
| `OpenTelemetry.Instrumentation.GrpcNetClient` | gRPC client calls |

Always set `RecordException = true` on AspNetCore and Http so exceptions become span events. Filter health checks so they do not flood Tempo:

```csharp
.AddAspNetCoreInstrumentation(o =>
{
    o.RecordException = true;
    o.Filter = ctx => !ctx.Request.Path.StartsWithSegments("/health")
                   && !ctx.Request.Path.StartsWithSegments("/metrics");
})
```

`SqlClient`: `SetDbStatementForText = true` captures the SQL text. Only enable if the SQL does not contain inline PII literals; prefer parameterized queries so literals are not in the statement.

## Custom spans (the high-value part)

Wrap business operations in spans from the shared `ActivitySource` (`Telemetry.Activity`, defined in the Core lib per `setup.md`):

```csharp
using var act = Telemetry.Activity.StartActivity("Underwriting.Decision");
act?.SetTag("loan.product", product);          // safe, low-cardinality
act?.SetTag("loan.amount_bucket", Bucket(amt)); // bucket, never raw amount
act?.SetTag("decision.outcome", outcome);

try
{
    var result = await _engine.DecideAsync(app);
    act?.SetTag("decision.score_band", result.Band);
    return result;
}
catch (Exception ex)
{
    act?.SetStatus(ActivityStatusCode.Error, ex.Message);
    act?.AddException(ex);                       // or RecordException via instrumentation
    throw;
}
```

Rules:
- Name spans by operation, not by data: `Underwriting.Decision`, not `Decide loan 8842`.
- Attributes are **low cardinality and PII-free**. Bucket amounts, use product codes, score bands. Never SSN/PAN/email/name/account.
- Set `ActivityStatusCode.Error` and attach the exception on failure so Tempo shows it red and the error links to logs.

## Span events and links

- **Events:** `act?.AddEvent(new ActivityEvent("cache.miss"))` for point-in-time markers inside a span.
- **Links:** for fan-out / batch / messaging where one operation relates to many traces, link instead of nesting: `StartActivity(name, ActivityKind.Consumer, links: new[] { new ActivityLink(parentContext) })`.
- **Kind:** set `ActivityKind` correctly (`Server`, `Client`, `Producer`, `Consumer`, `Internal`). RED metrics and service graphs depend on it.

## Context propagation

OTel .NET uses W3C Trace Context (`traceparent`) by default. `HttpClient` instrumentation injects it automatically. For messaging (SQS/SNS/Kafka), propagate manually:

```csharp
using OpenTelemetry;
using OpenTelemetry.Context.Propagation;
static readonly TextMapPropagator Propagator = Propagators.DefaultTextMapPropagator;
// inject on send:
Propagator.Inject(new PropagationContext(activity.Context, Baggage.Current), message.Attributes, (c, k, v) => c[k] = v);
// extract on receive, then start the consumer span with the extracted context.
```

Use **Baggage** for cross-service business context that should ride along (for example `tenant=cashmoney`), but never PII, baggage is sent on every downstream call.

## Sampling

- Local/dev: sample 100% (`ParentBasedSampler(new TraceIdRatioBasedSampler(1.0))`) so you see everything.
- Prod: either head-sample at a ratio (`TraceIdRatioBasedSampler(0.1)`) or, better, sample 100% at the app and **tail-sample at the collector** (keep all errors and slow traces, drop a fraction of fast successful ones). Tail sampling needs collector config, coordinate with SRE. `ParentBased` ensures a sampled parent keeps child spans.
- Span metrics (RED) are generated by Tempo from the spans it receives, so heavy head-sampling skews RED. Prefer tail sampling if RED accuracy matters.

## Exemplars (metrics jump to traces)

Set `SetExemplarFilter(ExemplarFilterType.TraceBased)` on the meter provider (`setup.md`, `metrics.md`). With it, histogram buckets carry a sampled `trace_id`, so a latency spike in Grafana links straight to an example trace.

## Export

`AddOtlpExporter()` sends to `OTEL_EXPORTER_OTLP_ENDPOINT` (or the per-signal traces endpoint). On EKS that is the node Alloy, which forwards to Tempo. On EC2/ECS it is the local collector/sidecar. See `deployment-targets.md`.

## Verify

In Grafana Explore (Tempo), TraceQL: `{resource.service.name="myservice" && resource.deployment.environment="local"}`. Or check `traces_spanmetrics_calls_total{service="myservice"}` in Mimir, if present, traces are flowing. See `verify.md`.
