# Good and Bad Tests

Concrete examples. The rules these illustrate are in the `code-rules` skill.

## Good tests

Test through the interface a caller uses, and assert on something a caller or operator can see.

```typescript
test("user can check out with a valid cart", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

What makes it good:

- It tests behaviour a caller cares about
- It uses the public interface only
- It survives an internal refactor
- The name describes WHAT, not HOW
- One logical assertion

## Bad tests

### Verifying around the interface instead of through it

```typescript
// BAD: reaches past the interface to the database
test("createUser saves to database", async () => {
  await createUser({ name: "Alice" });
  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});

// GOOD: reads back through the same interface a caller would use
test("createUser makes the user retrievable", async () => {
  const user = await createUser({ name: "Alice" });
  const retrieved = await getUser(user.id);
  expect(retrieved.name).toBe("Alice");
});
```

The bad version also couples the test to the table name and the column layout, so a schema change nobody depends on still breaks it.

### Asserting on collaborator calls

```typescript
// BAD: the assertion is about the implementation, not the outcome
test("checkout calls paymentService.process", async () => {
  const mockPayment = mock(paymentService);
  await checkout(cart, payment);
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total);
});
```

This passes even when the payment is never actually charged. Assert the outcome, or treat the interaction itself as the contract and test it at the boundary.

### Tautological assertions

```typescript
// BAD: the expected value is recomputed the way the code computes it
test("calculateTotal sums line items", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, i) => sum + i.price, 0);
  expect(calculateTotal(items)).toBe(expected);
});

// GOOD: the expected value is an independent literal
test("calculateTotal sums line items", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});
```

Red flags for this one: the test imports the same helper the production code uses to build the expected value, or a snapshot was generated by running the code rather than by working out the answer.

## Assert on what the contract promises

Match the assertion to the boundary:

| Boundary | Assert on |
| --- | --- |
| HTTP API | Status code, response body, headers, error shape |
| Persistence | State read back through a public query path |
| Messaging | The message published, the job enqueued, the webhook sent |
| CLI | Exit status, stdout, stderr |
| UI | Text, enabled and disabled state, navigation, visible errors |

Avoid asserting on exact log text unless the log line is itself the contract, and never assert on DOM structure the user cannot see.

## Table-driven tests

When one rule has many input and output pairs, drive it from a table rather than writing a test per case. The rule is the test, and the table is the data.

```typescript
test.each([
  [0, "none"],
  [1, "one"],
  [2, "many"],
])("label for %i items is %s", (count, expected) => {
  expect(label(count)).toBe(expected);
});
```
